# M3.2 S4A-R3 — Result Representation and Dispatch Authority Clarification

## Status

`R3_RESULT_AND_DISPATCH_AUTHORITY_CLARIFIED`

ACCEPTED NORMATIVE CLARIFICATION.

This clarification resolves only the confirmed implementation gaps required
to implement S4A-R3:

- latest eligible value;
- arithmetic mean;
- median;
- min;
- max;
- exact numeric helpers;
- R3 evidence accounting;
- the public execution boundary during the partial R3/R4 transition.

It does not change S1, S2, S3, R2 support binding, continuity, conflict
resolution, conversion authority, assessment, assembly, provenance,
production, persistence, or missing-opportunity semantics.

---

## 1. Confirmed result-representation gap

The accepted R3 numeric policy requires:

- `latest_eligible_value` to preserve the original accepted scalar;
- signed floating zero to remain signed for latest;
- arithmetic methods to produce canonical `ExactNumber`;
- `bool` never to be interpreted as numeric.

The current R1 `MethodValueResult.value` union:

`ExactNumber | str | bool`

cannot represent these semantics correctly:

- raw integer latest is rejected;
- raw float latest is rejected;
- raw `-0.0` may be coerced to `False`.

R3 MUST close this representation gap before executing latest.

---

## 2. Closed MethodValueResult value representation

The accepted method-result value domain becomes:

- `ExactNumber`
- strict `int`
- strict finite `float`
- strict `str`
- strict `bool`

Cross-kind coercion is forbidden.

In particular:

- float must never become bool;
- bool must never become int;
- int must never become float merely to satisfy validation;
- string must never be parsed into another scalar kind.

NaN and positive/negative infinity remain forbidden.

This widening is a result-envelope correction only.
It does not widen the accepted input evidence domain.

---

## 3. Method-specific representation rule

### latest_eligible_value

Latest MUST preserve the exact accepted original scalar kind.

For an accepted latest observation:

- integer input -> raw integer result;
- finite float input -> raw float result;
- `-0.0` -> raw `-0.0` result with negative sign preserved;
- string input -> raw string result;
- boolean input -> raw boolean result.

Latest MUST NOT convert a numeric scalar to `ExactNumber`,
because that would erase the original scalar representation and signed-zero
identity.

Latest does not accept NULL, ARRAY, or OBJECT as a value result.

### Arithmetic methods

The following methods MUST return `ExactNumber`:

- arithmetic_mean
- median
- min
- max
- within_segment_delta
- source_time_counter_rate
- historical_endpoint_slope
- any future authorized numeric missing_fraction result

For R3, only:

- arithmetic_mean
- median
- min
- max

are executed.

Arithmetic zero is canonical positive exact zero.

---

## 4. Numeric applicability

Mean, median, min, and max require finite numeric support.

`bool` is not numeric.

String, boolean, null, array, and object values MUST NOT be silently coerced
for arithmetic.

If authoritative support presented to an R3 numeric handler contains a
non-numeric value, execution raises:

`UnsupportedValueKindError`

This is a typed operation error, not an ordinary no-result.

---

## 5. Exact arithmetic

All R3 aggregate arithmetic uses normalized exact rational values.

Rules:

1. integer values remain exact;
2. finite float values use their exact binary integer ratio;
3. addition is rational integer arithmetic;
4. mean divides the exact sum by the exact positive cardinality;
5. median sorts by exact numeric value;
6. odd median returns the exact middle value;
7. even median returns the exact midpoint of the two middle values;
8. min and max compare exact numeric values;
9. no intermediate float conversion is permitted;
10. values larger than `2**53` remain exact;
11. very large integers must not overflow through float coercion;
12. arithmetic zero canonicalizes to `ExactNumber(0, 1)`.

---

## 6. Latest chronological selection

Latest uses the field contract's authoritative temporal basis.

- `SOURCE_OBSERVATION_TIME`
  -> `RuntimeObservation.observation_time`

- `GUARDIAN_RECEIPT_TIME`
  -> `RuntimeObservation.ingestion_time`

No clock fallback is permitted.

Latest selects the greatest authoritative selected time among the already
bound CURRENT support.

UUID ordering, ingestion ordering under source-time mode, page order,
caller order, provider name, source name, and value magnitude MUST NOT
select a winner.

If more than one bound support observation exists at the greatest selected
time, the result is:

`MethodNoResultReason.AMBIGUOUS_LATEST_TIME`

unless a future separately accepted authority explicitly establishes a
unique semantic winner.

R3 introduces no such winner authority.

---

## 7. Latest evidence accounting

For a successful latest result:

- every observation in the authoritative analytical set remains accounted
  exactly once;
- the selected latest observation is `USED`;
- earlier otherwise-authoritative current observations are `EXCLUDED` with
  the closed method-layer reason:

`method:not_latest_chronological_point`

This reason means only that the evidence was chronologically earlier for
this specific latest computation.

It does NOT mean:

- stale;
- invalid;
- conflicting;
- identity-mismatched;
- non-comparable;
- unusable for another method.

Existing artifact-derived exclusions remain unchanged and retain precedence.

---

## 8. Ambiguous-latest no-result accounting

For `AMBIGUOUS_LATEST_TIME`:

- every considered observation is `EXCLUDED`;
- existing artifact-derived exclusion reasons remain unchanged;
- otherwise-authoritative support observations use:

`method:ambiguous_latest_time`

No observation is `USED` in a `MethodNoResult`.

This reason does not select or rank tied observations.

---

## 9. Result-unit semantics

R3 value-producing methods use:

`MethodUnitSemantics(kind="FIELD_VALUE", ...)`

with the exact declared field `output_unit`.

No unit conversion is executed.

If a value-producing R3 method cannot establish the required field-value
unit semantics because the field result unit is undeclared, the ordinary
result is:

`MethodNoResultReason.RESULT_UNIT_SEMANTICS_UNDECLARED`

For otherwise-authoritative support observations in this no-result case,
the closed method-layer reason is:

`method:result_unit_semantics_undeclared`

Existing more-specific artifact-derived exclusion reasons retain precedence.

---

## 10. Aggregate evidence accounting

For successful:

- arithmetic_mean;
- median;
- min;
- max;

all observations in the authoritative analytical support set remain `USED`.

For min/max, all equal-valued extrema therefore remain retained.
No hidden winner is selected among ties.

R3 does not introduce per-observation "not min", "not max", or
"not median" exclusion reasons because all authoritative support
participates in determining those aggregate results.

---

## 11. R3 execution boundary

R3 MUST NOT accept a caller-supplied `AuthoritativeAnalyticalSet` as
execution authority.

Every R3 execution path MUST start from:

- `MethodConfiguration`; and
- `AuthoritativeMethodInput`.

The implementation MUST internally call the accepted
`bind_method_support(...)` boundary.

This preserves the R2 anti-forgery rule.

---

## 12. Public dispatcher during R3

R3 implements only:

- latest_eligible_value;
- arithmetic_mean;
- median;
- min;
- max.

The historical arithmetic methods remain R4 work.

To avoid exposing a public dispatcher that has placeholder behavior for
recognized-but-not-yet-implemented R4 methods:

`compute_method` remains absent during R3.

R3 may add private execution helpers for its five methods.

The public `compute_method` dispatcher is deferred until an implementation
slice can provide semantically honest handling for every recognized method
that it dispatches.

No "not implemented" `MethodNoResult` may be invented.

No recognized R4 method may be falsely reported as an unknown method.

---

## 13. MethodExecutionLimits

R3 introduces no `MethodExecutionLimits`.

R3 consumes only the already bounded authoritative S2/S3 evidence graph.

Existing accepted record/page/byte/scan ceilings remain authoritative.

R3 arithmetic must be bounded by the authoritative support cardinality and
must not introduce unbounded external work.

A future separate limit object requires separate accepted authority.

---

## 14. R3 private-handler boundary

Private R3 execution helpers may be introduced only in
`state/methods.py`.

They must:

1. accept validated configuration plus authoritative input;
2. internally obtain support through `bind_method_support`;
3. propagate an existing binder `MethodNoResult` unchanged;
4. never trust caller-authored support membership;
5. perform no S3 admission, identity, conflict, or continuity recomputation;
6. execute no conversion;
7. access no wall clock;
8. access no provider, miner, GPU, filesystem, database, or network;
9. use no randomness;
10. mutate no input artifact.

---

## 15. R3 determinism

For equal authoritative semantic input, R3 output must be identical.

Mean, median, min, and max are invariant to non-semantic caller ordering.

Latest is determined solely by the authoritative temporal basis.

Exact rational arithmetic must not depend on Python float accumulation
order.

UUID sorting may be used only for canonical presentation/accounting,
never to choose a semantic value winner.
