## R4-02 — Controller-state mutual exclusivity

**Status: PASS**

The controller-state invariants now define mutually exclusive meanings:


## R4-03 — VALID / non-VALID RewardTargetAssessment invariants

**Status: PASS**

The contract is now symmetric.

```text
assessment_quality = VALID
    current_reward_state required
    signed_target_gap required
    performance_state required
```

and:

```text
assessment_quality != VALID
    signed_target_gap = null
    performance_state = null
```

This prevents a semantically incomplete `VALID` assessment and prevents non-valid evidence from generating target-seeking pressure.

`current_reward_uncertainty` remains intentionally optional at the architecture layer and may be strengthened by later statistical-method contracts.

# Signed target-gap freeze verification

**Status: PASS**

The v0.4/v0.4.1 convention remains deterministic:

```text
positive = unmet shortfall
zero     = acceptable target region
negative = above acceptable target region
```

For `MINIMUM`:

```text
current < target
    BELOW_TARGET
    gap = target - current

current == target
    WITHIN_TARGET_BAND
    gap = 0

current > target
    ABOVE_TARGET
    gap = target - current
```

For `BAND [lower, upper]`:

```text
current < lower
    BELOW_TARGET
    gap = lower - current

lower <= current <= upper
    WITHIN_TARGET_BAND
    gap = 0

current > upper
    ABOVE_TARGET
    gap = upper - current
```

No alternate interpretation remains open to implementation.

# Accepted non-blocking implementation notes

These are not freeze blockers.

## NB-01 — Verification protocol may become more explicit during implementation

The Evaluation Protocol already requires deterministic contract testing for the target model.

During implementation, the M3.5 handoff should explicitly instantiate tests for:

```text
NO_ACTIVE_TARGET
ASSESSMENT_UNAVAILABLE
ACTIVE

VALID
UNCERTAIN
STALE
INVALID
```

including all required/nullability invariants.

This strengthens verification coverage without changing architecture semantics.

## NB-02 — current_reward_uncertainty is intentionally method-dependent

At M3.0 architecture level:

```text
current_reward_uncertainty?
```

may remain optional.

A later statistical contract may make uncertainty mandatory for specific estimation/prediction methods.

This is an accepted deferred implementation detail, not semantic ambiguity.

## NB-03 — target urgency cannot modify ADR-0006 implicitly

Target urgency / reevaluation-trigger orchestration may cause a new Decision evaluation.

It does not authorize hidden weighting, hidden scoring bonuses, or modification of:

```text
DUS = (Benefit × Confidence) - (Risk + ActionCost + Uncertainty)
```

Any such change would require an explicit superseding ADR.
