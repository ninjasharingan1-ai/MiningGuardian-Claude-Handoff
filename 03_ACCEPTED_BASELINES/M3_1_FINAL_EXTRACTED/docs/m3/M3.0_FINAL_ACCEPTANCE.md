## 2. Scope accepted by M3.0

M3.0 defines architecture, semantics, ownership, contracts, safety boundaries, verification rules, runtime-evidence requirements, and staged progression for MiningGuardian's transition from the frozen M2 decision system toward a safe autonomous mining cognitive-control system.

The accepted mission loop is:

```text
Observe
→ Understand
→ Estimate State
→ Predict
→ Compare Against Reward Target
→ Decide
→ Authorize Safely
→ Execute only in future approved phases
→ Measure Outcome
→ Evaluate Reward
→ Learn
→ Propose Verified Updates
→ Promote Explicitly
```

M3.0 itself grants **no live execution authority**.

## 4. Accepted M3.0 core boundaries

### Reward Target Authority

`RewardTargetAuthority` owns:

- target creation;
- target change;
- target retirement;
- target identity/version;
- objective type;
- economic unit/basis;
- RewardContract binding.

It is separate from M2 Policy and from runtime target tracking.

### Reward Target Controller

`RewardTargetController` owns:

- active-target consumption;
- `controller_status`;
- assessment orchestration;
- evaluation-window initiation/orchestration;
- assessment consumption for control-loop orchestration;
- reevaluation-trigger orchestration.

It does not own RewardTargetAssessment semantics.

### RewardTargetAssessment

`RewardTargetAssessment` owns:

```text
assessment_quality
current_reward_state
performance_state
signed_target_gap
attainability
attainability_reason
```

Lifecycle, controller availability, assessment quality, reward performance, signed gap, and attainability remain distinct concepts.

## 5. Frozen reward-target semantics

Runtime RewardTarget supports only:

```text
MINIMUM
BAND
```

`MAXIMIZE` is a higher-level strategic optimization objective and is not a RewardTarget setpoint type.

The frozen signed-gap convention is:

```text
positive  = unmet shortfall
zero      = inside acceptable target region
negative  = above acceptable target region
```

For `MINIMUM`:

```text
current < target
    BELOW_TARGET
    gap = target - current

current == target
    WITHIN_TARGET_BAND
    gap = 0

current > target
    ABOVE_TARGET
    gap = target - current
```

For `BAND [lower, upper]`:

```text
current < lower
    BELOW_TARGET
    gap = lower - current

lower <= current <= upper
    WITHIN_TARGET_BAND
    gap = 0

current > upper
    ABOVE_TARGET
    gap = upper - current
```

No implementation may silently reinterpret this sign convention.

## 6. Frozen controller and assessment invariants

`RewardTargetControllerState`:

```text
NO_ACTIVE_TARGET
    active_reward_target_id = null
    latest_assessment_id = null
    target-seeking pressure = false

ASSESSMENT_UNAVAILABLE
    active_reward_target_id required
    latest_assessment_id = null
    target-seeking pressure = false

ACTIVE
    active_reward_target_id required
    latest_assessment_id required
```

`RewardTargetAssessment`:

```text
assessment_quality = VALID
    current_reward_state required
    signed_target_gap required
    performance_state required

assessment_quality != VALID
    signed_target_gap = null
    performance_state = null
    attainability = UNKNOWN
    decision_evaluation_required = false
```

Target attainability is:

```text
ATTAINABLE
UNREACHABLE_SAFELY
UNKNOWN
```

Therefore this remains valid:

```text
performance_state = BELOW_TARGET
attainability = UNREACHABLE_SAFELY
```

The system may recognize that a target is missed while refusing unsafe pursuit.

## 7. RewardContract and RewardEvaluationWindow

Every target/reward comparison must bind to explicit versioned semantics.

`RewardContract` defines the economic reward metric, unit, credited-work/accounting rules, included realized costs, exclusions, missing-data behavior, and maturity/calculation semantics.

Decision-time ADR-0006 penalties remain separate from realized reward accounting.

Do not double-count:

```text
Risk
predicted ActionCost
Uncertainty
```

inside realized Reward unless an explicit future superseding contract/ADR changes the architecture.

`RewardEvaluationWindow` remains distinct from:

```text
Control Evaluation Interval
Statistical Estimation Horizon
Prediction Horizon
Pool Accounting Window
Network Block Interval
Outcome Observation Window
Reward Attribution Window
Cooldown / Dwell Interval
```

## 8. Outcome / Reward / Learning / Promotion acceptance

Outcome supports:

```text
PERFORMANCE_WINDOW
ACTION_ATTRIBUTED
```

`PERFORMANCE_WINDOW` does not require Decision, Action, or Execution.

`ACTION_ATTRIBUTED` requires explicit attribution/reference evidence before it may support Learning or Promotion.

Reward is computed from mature Outcome evidence and is never copied from Prediction.

Learning may produce:

```text
LearningArtifact
→ UpdateProposal
→ Offline / Replay Verification
→ PromotionDecision
→ Active Version
```

No direct `LearningArtifact → Active Version` path is accepted.

## 9. Safe-control boundary

M2 Policy remains candidate admissibility authority.

Future post-decision execution uses a separate runtime path:

```text
DecisionResult
→ ActionRequest
→ Capability Gate
→ Execution Safety Gate
→ Freshness Gate
→ Stability / Rate Gate
→ Rollback Gate
→ Human Approval Gate when required
→ ExecutionAuthorization
→ Execution Adapter
→ ExecutionRecord
```

Safe Control may block or request reevaluation.

Safe Control may not re-score, re-rank, silently replace the selected candidate, or become a second M2 Policy.

No LLM may directly actuate hardware/process controls.

M3.0 intentionally does not choose the concrete database/storage technology.

## 11. Safety and continuity priorities

The accepted priority order is:

```text
Hardware Safety
> Mining Continuity
> Evidence Quality / Observability
> Constraint Compliance
> Net Effective Reward Objective
> Energy Efficiency
> Exploration / Learning
```

Restart/switch churn is explicitly treated as costly and potentially pathological.

Target pursuit never overrides safety, continuity, stale-data handling, capability limits, cooldown, dwell, rollback requirements, or authorization gates.

## 13. Accepted non-blocking notes

These are accepted implementation notes, not M3.0 release blockers.

### NB-01 — verification details

Later implementation handoffs should instantiate deterministic tests for controller-state and assessment-quality invariants.

This strengthens verification and does not change M3.0 semantics.

### NB-02 — method-dependent uncertainty

`current_reward_uncertainty` may remain optional at the architecture layer.

A later statistical-method contract may make it mandatory where appropriate.

### NB-03 — target urgency

Target urgency / reevaluation-trigger orchestration may request a new Decision evaluation.

It does not authorize hidden weights, hidden bonuses, or silent modification of ADR-0006.
