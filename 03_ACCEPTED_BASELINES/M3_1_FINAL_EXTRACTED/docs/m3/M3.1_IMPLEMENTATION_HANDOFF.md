# 12. Time Contract

M3.1 MUST preserve the frozen M3.0 glossary semantics.

The frozen definitions are authoritative:

## observation_time

```text
when the source recorded the observation
```

This is the source-recorded observation timestamp.

It may be unavailable when the source does not provide a trustworthy timestamp.

If unavailable:

```text
observation_time = null
```

Do not substitute MiningGuardian receipt time for a missing source observation timestamp.

## ingestion_time

```text
when MiningGuardian received the observation
```

This is the MiningGuardian receipt/acquisition timestamp.

It must be recorded by the canonical M3 runtime-observation path.

## event_time

`event_time` is optional and may be used only when the source explicitly distinguishes:

```text
the underlying event occurrence time
```

from:

```text
the time the source recorded the observation
```

If the source exposes only one source timestamp for the recorded observation:

```text
store it as observation_time
event_time = null
```

Do not duplicate the same timestamp into both fields merely to populate them.

## processing_time / canonicalization_time

If the implementation needs to record when MiningGuardian transformed the received source data into a canonical runtime observation, use an additional implementation-level timestamp such as:

```text
processing_time
```

or:

```text
canonicalization_time
```

This additional timestamp is NOT a replacement for the frozen meanings of:

```text
observation_time
ingestion_time
```

Its exact field name must follow repository conventions and remain clearly documented as implementation-level processing/canonicalization time.

Do not silently redefine any frozen timestamp term.

# 17. Missing vs Zero

Zero is a value.

Missing is a quality/data-availability condition.

Therefore:

```text
0 ≠ MISSING
```

Examples:

```text

```

means:

```text
successful read, no active throttle reasons
```

if capability evidence confirms the field was read successfully.

It must not collapse to the same representation as:

```text
field could not be read
```

The same principle applies to:

```text
hashrate
latency
share counters
power
utilization
```

# 19. Delayed vs Stale

Use these semantics:

## DELAYED

```text
the observation arrived materially later than expected
relative to the source/event timing contract
```

Requires enough clock/source information to establish delay.

If source event time is unavailable:

```text
do not classify DELAYED from guesswork
```

## STALE

```text
the observation was once valid/current
but is now too old for its configured freshness contract
```

Delay concerns transport/acquisition lateness.

Staleness concerns current age/usefulness.

They must not be treated as synonyms.

# 54. Stop Conditions

Stop implementation and report BLOCKED if:

```text
a required change would alter a frozen M2 semantic contract

a required change would alter accepted M3.0 architecture semantics

the implementation requires inventing control authority

the implementation requires destructive migration without an accepted migration plan

canonical source identity cannot be represented without guessing

a source field requires undocumented unit/meaning and the code would need to invent it
```

Do not code around an architecture ambiguity by silently choosing a meaning.

---

# 55. Final Rule

M3.1 succeeds when MiningGuardian can answer:

```text
What did we observe?
From which source instance?
When did the source event occur, if known?
When did we observe it?
When did we ingest it?
What unit is the value in?
What is its quality?
How fresh is it?
Which acquisition/session does it belong to?
What provenance supports it?
Can we persist and reconstruct it losslessly?
```

without answering questions that belong to later phases:

```text
What is the hidden state?
What will happen next?
What should we do?
Should we execute?
What reward did the action cause?
What should the controller learn?
```

That separation is the core success condition for M3.1.
