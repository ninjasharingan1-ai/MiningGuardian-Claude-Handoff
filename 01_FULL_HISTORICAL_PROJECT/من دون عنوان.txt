# MiningGuardian M3.2 — SEMANTIC CONTRACT RESOLUTION

## 1. Mission

Resolve ONLY the semantic blockers identified by the completed:

```text
M3.2 READ-ONLY PREFLIGHT
```

The preflight verdict was:

```text
BLOCKED_BY_SEMANTIC_CONFLICT
```

This task must convert those unresolved decisions into explicit, internally consistent M3.2 contracts.

Do NOT implement code.

without allowing Codex to invent semantics during coding.

# 4. Resolve Blocker A — EstimatedState validity

Define what makes an `EstimatedState` field valid.

Do not require the entire snapshot to be all-or-nothing unless frozen authority requires it.

The preferred semantic model should evaluate whether:

```text
individual estimated fields
```

can independently be:

```text
VALID
DEGRADED
UNKNOWN
INVALID
```

or an equivalent explicit vocabulary.

Resolve:

```text
Can a snapshot contain both valid and unavailable fields?

Can an EstimatedState snapshot exist when one domain is missing?

What makes the snapshot itself usable?

What makes a single field usable?

How is a field represented when evidence is insufficient?
```

Do NOT use numeric zero to represent unavailable state.

Do NOT silently copy M2 ContextValidity semantics.

Provide explicit invariants.

---

# 5. Resolve Blocker B — State confidence

Define `StateConfidence` as a distinct concept.

It must NOT be:

```text
M2 Decision Confidence
Observation Quality
Freshness
Evidence Reliability
```

Define what confidence means semantically.

Recommended interpretation to evaluate:

```text
confidence = strength of support for the current estimated value
given the available evidence and estimator method
```

Resolve whether confidence should initially be:

```text
categorical
numeric
or structured
```

Prefer the simplest deterministic contract that does not create false precision.

If numeric confidence cannot be justified from current evidence:

```text
do not invent a probability
```

A categorical model such as:

```text
HIGH
MEDIUM
LOW
UNKNOWN
```

may be considered if consistent with frozen architecture.

Do not adopt it automatically; justify the final choice.

---

# 6. Resolve Blocker C — State uncertainty

Define `StateUncertainty` separately from confidence.

It should capture what remains unresolved about the estimated state.

Consider whether uncertainty needs structured dimensions such as:

```text
measurement uncertainty
temporal uncertainty
source disagreement
evidence incompleteness
identity uncertainty
method limitation
```

Do not force these into a single fake numeric score unless justified.

Resolve:

```text
Can confidence be high while some known limitation remains?

Can uncertainty be present while a field is still usable?

How should unknown uncertainty differ from known uncertainty?
```

---

# 7. Resolve Blocker D — Evidence completeness

Define the minimum evidence requirement for producing an estimated field.

Do not define one universal minimum for every field.

Create a rule such as:

```text
each state field declares its required evidence contract
```

The contract may distinguish:

```text
REQUIRED evidence
OPTIONAL supporting evidence
CONFLICTING evidence
UNAVAILABLE evidence
```

Resolve how evidence completeness influences:

```text
validity
confidence
uncertainty
limitations
```

without collapsing them into one field.

---

# 8. Resolve Blocker E — Reference time

Define one authoritative:

```text
state_reference_time
```

for an EstimatedState snapshot.

It must represent:

```text
the current-state instant against which included evidence is evaluated
```

Resolve whether it should normally be:

```text
explicitly supplied by caller
```

rather than implicitly calling the wall clock inside reconstruction.

Preferred determinism rule:

```text
same observations
+
same configuration
+
same reference time
+
same method version
=
same EstimatedState
```

Do not allow reconstruction to depend silently on current wall clock.

---

# 9. Resolve Blocker F — Temporal alignment

Define how observations from different sources are allowed to contribute to the same state snapshot.

Account for:

```text
different polling cadence
missing source observation_time
receipt-time-only evidence
stale observations
out-of-order observations
clock disagreement
reset/discontinuity
```

Do NOT require exact timestamp equality.

Define an explicit alignment policy based on:

```text
reference time
source timestamp availability
freshness
allowed evidence window
quality
```

Do not reuse legacy future-time clamping.

Future/inconsistent timestamps must not silently become fresh.

---

# 10. Resolve Blocker G — Source disagreement

Define a first-class representation for conflicting evidence.

Do NOT silently choose:

```text
latest source
preferred source
highest value
lowest value
```

unless an explicit source-authority rule exists.

Distinguish:

```text
source disagreement
source failure
missing evidence
identity mismatch
temporal misalignment
```

A conflict should remain visible in provenance/limitations.

Resolve whether conflicting evidence can produce:

```text
a degraded estimate
an unknown estimate
an invalid estimate
```

based on field-specific rules.

Do not invent universal resolution precedence where none is justified.

---

# 11. Resolve Blocker H — Stale evidence

Define how stale evidence affects state.

Stale evidence may remain historically valid evidence but should not automatically support current state.

Resolve:

```text
Can stale evidence contribute to a degraded field?

When must stale evidence be excluded?

Can a last-known value be retained as context while state validity becomes UNKNOWN?

How are limitations recorded?
```

Do not relabel stale data as current.

---

# 12. Resolve Blocker I — Discontinuity and counters

Define rules for cumulative counters and rate-like features.

Counter reset/discontinuity must prevent unsafe delta/rate calculation across the discontinuity.

Resolve:

```text
when a rate is unavailable
when a new continuity segment begins
what provenance must identify the segment
how uncertainty is represented when incarnation is unknown
```

Do not infer miner restart solely from a counter or uptime decrease.

---

# 13. Resolve Blocker J — Current-state features

Classify permitted M3.2 derived features.

Examples:

```text

median
min/max

rate
slope over historical window

```

These may remain:

```text

```

```text
historical slope ≠ prediction
```

# 15. Resolve Blocker L — Estimation method versioning

At minimum an EstimatedState field or snapshot should identify:


Do NOT build a general ML model registry in M3.2 unless required.

The initial system may use deterministic statistical methods.

# 16. Resolve Blocker M — Derived-state persistence

Resolve whether M3.2 uses:

```text
reconstruction only
persistence only
or
both
```

Evaluate against frozen requirements:

```text
raw M3.1 evidence remains authoritative
derived state must be reproducible
persistence must not re-estimate during load
```

Preferred architecture to evaluate:

```text
M3.1 RuntimeObservation
        ↓
deterministic estimator
        ↓
EstimatedState
        ↓
optional versioned derived-state persistence
```

If EstimatedState is persisted:

```text
load must restore
not re-run estimator
```

Raw observations remain source authority.

A persisted state is a versioned derived artifact, not replacement evidence.
