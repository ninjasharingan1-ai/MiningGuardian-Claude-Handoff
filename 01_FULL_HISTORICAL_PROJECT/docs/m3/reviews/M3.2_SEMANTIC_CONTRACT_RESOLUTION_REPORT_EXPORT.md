# M3.2 SEMANTIC CONTRACT RESOLUTION REPORT

## 1. Executive Decision

The semantic design is resolved as a **proposed contract set requiring three ADR acceptances before implementation**.

The principal decisions are:

- Evaluate validity independently for each estimated field.
- Permit partially usable snapshots.
- Represent confidence as structured evidence support, without invented probabilities.
- Preserve quantified uncertainty, unquantified limitations, and missing evidence separately.
- Require an explicit reference time and bounded, reproducible evidence selection.
- Keep receipt-only context distinguishable from evidence of current physical state.
- Represent unresolved disagreement explicitly.
- Support deterministic estimation and optional, immutable derived-state persistence through separate operations.
- Admit economic values only when their identity, units, timing, and source semantics are established.

These proposals do not change frozen M2, M3.0, or M3.1 contracts. No files were modified, tests run, providers contacted, or implementation performed.

## 5. State Field Validity

`StateValidity` has four values:

| ValidityMeaningValueUsability |                                                                                                              |          |                                                                |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------ | -------- | -------------------------------------------------------------- |
| `VALID`                       | Required evidence, identity, temporal and method conditions are satisfied; no qualifying degradation applies | Required | Usable for its declared estimand                               |
| `DEGRADED`                    | A value remains supported under an explicitly permitted limitation or fallback                               | Required | Usable only for the field’s declared restricted interpretation |
| `UNKNOWN`                     | Evidence cannot establish the requested value                                                                | Null     | Unavailable                                                    |
| `INVALID`                     | A detected integrity, identity, dimensional or method violation prevents a defensible artifact               | Null     | Unavailable; failure reason required                           |

Required invariants:

1. Missing, stale-only or insufficient evidence normally produces UNKNOWN, not zero.
2. An unresolved conflict between plausible eligible values produces UNKNOWN by default.
3. INVALID requires positive evidence of a violation; absence alone is insufficient.
4. Corrupted input does not invalidate independent fields.
5. Rejected evidence may coexist with a VALID field only when the field contract still establishes sufficient, unambiguous support.
6. DEGRADED requires a named rule. It is not a general escape hatch.
7. A non-null diagnostic or last-known value must not occupy the unavailable current-value slot.
8. Field validity grants no policy admissibility or execution permission.

The validity evaluator belongs to state estimation. Persistence restores its recorded result rather than reevaluating it.

## 6. Snapshot Partial-Validity Model

**A snapshot may contain valid, degraded, unknown and invalid fields simultaneously.**

A missing economic domain does not invalidate independently supported hardware or miner fields. A failed GPU observation does not erase supported miner state.

Snapshot summary:

- `COMPLETE`: every requested field is VALID.
- `PARTIAL`: at least one requested field is VALID or DEGRADED, but COMPLETE does not apply.
- `UNAVAILABLE`: no requested field has a usable value.

Structural snapshot failure—such as inconsistent reference times or duplicate field identities—is a construction/load error, not an ordinary completeness state.

Additional requirements:

- Requested-but-unavailable fields remain explicit.
- Unrequested fields are distinguishable from unavailable fields.
- Summary counts and field-key lists must agree with field records.
- An entirely unavailable snapshot may exist as a diagnostic artifact.
- Consumers evaluate their required field subset and whether they accept DEGRADED results. There is no universal “safe to use” boolean.

## 7. State Confidence Contract

**Chosen representation: structured support assessment without a numeric aggregate or HIGH/MEDIUM/LOW scale.**

The current repository supplies no calibration evidence or accepted thresholds that justify those grades. Frozen M2 also deliberately avoids unsupported numeric mappings in [DecisionConfidenceEngine (line 54)]\(C:/MiningGuardian/src/mining_guardian/agent/decision/confidence.py:54).

`StateConfidence` means:

> Strength and completeness of the evidence-based justification for this particular estimated value under its declared method and assumptions.

Required fields:

```
interpretation = CURRENT_ESTIMATE_SUPPORT
rubric_id
rubric_version
support_status
support_checks
reason_codes
limitations
```

`support_status`:

- `SUPPORTED`: all applicable support checks pass.
- `LIMITED`: minimum estimation requirements pass, but a strengthening check fails or remains unknown.
- `UNASSESSED`: no value exists, or the available method/evidence cannot assess support.

Each check records its identifier, PASS/FAIL/UNKNOWN/NOT_APPLICABLE result and supporting references. Checks can cover sample adequacy, representativeness, method assumptions and independent corroboration.

The field contract must distinguish **minimum validity requirements** from **confidence-strengthening checks**. This permits a valid estimate with LIMITED support.

Forbidden interpretations:

- Probability of correctness.
- Observation quality copied into a new field.
- Freshness converted into a score.
- M2 DecisionConfidenceResult or prediction confidence.
- Authentication or proof that a source is truthful.

Owner: state-estimation method. Persist and restore the assessment unchanged.

## 8. State Uncertainty Contract

`StateUncertainty` describes unresolved uncertainty around the estimated value, with these required dimensions:

```
measurement
temporal
source_disagreement
evidence_incompleteness
identity
method
```

Each dimension contains:

```
assessment_status
reason
evidence_refs
quantification, if available
```

Statuses:

- `QUANTIFIED`: explicit magnitude, interval or other accepted quantitative representation.
- `KNOWN_UNQUANTIFIED`: a particular limitation is established, but its magnitude is unavailable.
- `UNKNOWN`: insufficient evidence even to characterize it.
- `NOT_APPLICABLE`: justified by the field definition.

Quantification requires units, method/version, assumptions and coverage interpretation where applicable.

The frozen glossary defines uncertainty as quantified lack of certainty. Therefore **KNOWN_UNQUANTIFIED is an uncertainty-assessment status, not a claim that a quantitative uncertainty value exists**. Its quantitative value remains null; the known issue also appears in limitations.

Consequences:

- Strong support and a known limitation can coexist.
- A usable field can retain uncertainty.
- Unknown uncertainty is not zero uncertainty.
- Sample variation is not automatically measurement error or a confidence interval.
- No synthetic aggregate uncertainty score is introduced.

Owner: state-estimation method; economic methods use the same structure. Persistence preserves all dimensions.

## 9. Evidence Completeness Contract

Every field requires a versioned `FieldEvidenceContract` defining:

```
estimand and subject scope
required signals and source semantics
optional support
identity requirements
units and allowed conversions
admissible quality conditions
temporal basis and bounded window
minimum sample count and span
coverage/gap requirements
continuity requirements
conflict behavior
permitted degradation
confidence rubric
output domain
resource limits
```

No universal minimum applies.

Natural mathematical minima do not imply statistical sufficiency:

- Mean/median/min/max: at least one eligible value.
- Delta: at least two ordered eligible values.
- Rate/slope: at least two distinct eligible times and positive elapsed time.
- Missing fraction: an explicit denominator.

A field contract may demand more. Deployment-dependent durations and thresholds must be explicit configuration inputs, versioned and retained. Missing required configuration is a configuration error; implementation must not choose a convenient threshold.

Completeness records required, satisfied, unavailable, conflicting and optional requirements separately.

Effects remain distinct:

- Failed minimum requirement → UNKNOWN.
- Permitted shortfall → DEGRADED.
- Missing optional strengthening evidence → confidence limitation.
- Unknown magnitude of a shortfall’s effect → uncertainty.
- All reasons remain in limitations and provenance.

## 10. Reference-Time Contract

`state_reference_time` is mandatory, caller-supplied, timezone-aware UTC.

It is the instant whose current state is being estimated—not source recording time, receipt time, persistence time or reconstruction execution time.

Rules:

1. All fields in one snapshot use the same reference time.
2. Fields retain their own support intervals and source timestamps.
3. Historical replay supplies the historical reference time explicitly.
4. Estimation must not call the wall clock internally.
5. Evidence received after the reference time cannot support an as-of estimate for that time.
6. If recorded processing time establishes that an observation was not yet canonicalized, that later availability must also be respected.
7. Missing processing time does not prove the observation was historically consumed by a decision.

`estimated_at` retains the frozen meaning of artifact production time. It is supplied through explicit production metadata and is not substituted for the reference time. Section 18 defines its treatment in determinism.

## 11. Temporal Alignment Contract

Exact timestamp equality is unnecessary. Each field uses an explicit bounded window:

```
(T − W, T]
```

where `T` is the reference time and `W` is supplied by the field contract/configuration.

Two evidence bases remain separate:

| BasisPermitted interpretation |                                                                                             |
| ----------------------------- | ------------------------------------------------------------------------------------------- |
| Source recording time         | Current-state estimation when clock, age, quality and method conditions permit              |
| Guardian receipt time         | What Guardian received during a bounded interval; does not establish source measurement age |

Initial rules:

- No silent source-time-to-receipt-time substitution.
- Receipt-only readings may appear in descriptive or last-reported context.
- A physical-current-state field requiring known measurement age becomes UNKNOWN when that age cannot be established.
- Cross-source arithmetic requires proven subject correspondence, compatible quantities and an explicit maximum temporal separation.
- Receipt proximity and shared acquisition ID do not prove physical simultaneity.
- Event time is used only when the field’s source contract specifically requires it.
- Future timestamps and inconsistent clock order are excluded from current-value support; never clamped to zero age.
- Delayed/out-of-order observations can support historical calculations when their clocks and ordering are interpretable and they were available by the cutoff.
- Acquisition-time quality and freshness remain immutable; M3.2 adds a separate assessment at `T`.

This intentionally preserves the UNKNOWN source age of current [NVMLObserver (line 23)]\(C:/MiningGuardian/src/mining_guardian/observability/nvml.py:23) and [miner canonicalization (line 41)]\(C:/MiningGuardian/src/mining_guardian/observability/miner.py:41).

The legacy future-age clamp in [agent/temporal.py (line 56)]\(C:/MiningGuardian/src/mining_guardian/agent/temporal.py:56) is not reused.


Optional:

```

```

Distinguish:

- `VALUE_DISAGREEMENT`
- `IDENTITY_MISMATCH`
- `TEMPORAL_MISALIGNMENT`
- `UNIT_OR_SEMANTIC_MISMATCH`

Source failure and missing evidence are availability conditions, not value disagreement.

A value conflict requires comparable claims: same subject, quantity, unit and compatible effective interval. Miner raw hashrate and pool calculated hashrate are not automatically competing measurements of one quantity.

Initial resolution:

- No cross-provider averaging or implicit winner.
- Unresolved, comparable competing values → UNKNOWN.
- Integrity/identity corruption preventing defensible attribution → INVALID.
- DEGRADED is allowed only under an explicit versioned resolution rule.
- No general conflict-resolution rule is enabled initially.
- All participants remain traceable, including rejected ones.

Within-stream chronological selection is permitted only by a named estimator such as `latest_observed_value`; it is not a cross-source authority policy. Ambiguous same-position/same-time values require explicit ordering evidence or conflict treatment.

## 13. Stale/Missing Evidence Contract

Chosen rules:

1. Stale-only evidence cannot populate a current-value field.
2. A last-known value may remain in a separate context object containing its value, source time if known, receipt time, age assessment and observation reference.
3. UNKNOWN current state does not erase that historical context.
4. Older evidence may contribute to a descriptive historical window if that window includes it.
5. A window statistic used to estimate current state must additionally meet its declared terminal-recency, coverage and method requirements.
6. Old inputs are not individually relabeled fresh because the resulting snapshot is new.
7. No interpolation, forward fill or imputation is enabled implicitly.

A later field-specific stale fallback would require a new accepted method contract. M3.2’s initial contract does not provide a generic stale-value DEGRADED fallback.

For a latest-value estimator, a newer explicit invalidation/failure cannot be hidden by silently falling back to an older successful reading. Any retained older value is last-known context unless the field explicitly permits that fallback.

## 14. Continuity / Reset Contract

A continuity segment is an **analytical evidence segment**, not a miner process identity.

Its required provenance includes:

```
source and source instance
signal
explicit workload/algorithm scope where relevant
segment anchor observation
ordering basis
boundary reason/evidence
incarnation identity, if established
continuity method/version
```

Break a segment on:

- Explicit incarnation change.
- Counter decrease that cannot be safely ordered/resolved.
- Recorded reset/discontinuity.
- Subject, workload, algorithm or counter-semantic change.
- A gap exceeding the field’s explicit continuity allowance.
- An unresolved ordering or identity conflict.

Rules:

- Never calculate delta/rate across a boundary.
- Never clamp a negative counter delta to zero.
- No implicit rollover correction.
- A new segment needs its own minimum supporting samples.
- Unknown incarnation remains unknown.
- Uptime decrease does not prove restart.
- Equal values do not establish duplication.

Initial rate semantics are **observed source-counter change per unit time**. Interpreting that as complete physical activity requires a source contract establishing counter scope and continuity. When only observed continuity is supported, the result must retain that limitation and cannot be presented as exact credited work.

Receipt-only timing does not support a physical share rate in the initial contract.

Current [ContinuityTracker (line 33)]\(C:/MiningGuardian/src/mining_guardian/observability/continuity.py:33) provides useful diagnostics, but its process-local history is not the reconstruction authority. M3.2 must derive segments reproducibly from the selected evidence.

## 15. Current-State Feature Boundary

Permitted deterministic descriptive methods:

| FeatureExact initial meaning |                                                                                     |
| ---------------------------- | ----------------------------------------------------------------------------------- |
| Sample mean                  | Arithmetic mean of eligible recorded values; not a time-weighted mean               |
| Median                       | Middle ordered value, or arithmetic mean of the two middle values                   |
| Min/max                      | Extremes of eligible values in the declared window                                  |
| Delta                        | Last eligible value minus first, within one admissible scope/segment                |
| Counter rate                 | Eligible counter delta divided by positive source-time interval                     |
| Historical slope             | Endpoint change divided by elapsed historical time; explicitly named endpoint slope |
| Missing fraction             | Missing required opportunities divided by explicitly defined expected opportunities |

Additional rules:

- No extrapolation beyond the reference time.
- No implicit resampling or smoothing.
- Irregular sampling must remain visible.
- Missing fraction is UNKNOWN when expected opportunities cannot be established; observed row count does not reveal completely absent acquisitions.
- Non-finite results are rejected.
- Counter methods obey section 14.
- Algorithm-specific H/s values are never aggregated as equivalent economic output.

Historical slope is not prediction. Prediction begins when an artifact claims a future value/state.

Legacy [\_mean, \_delta and \_slope (line 74)]\(C:/MiningGuardian/src/mining_guardian/agent/context.py:74) illustrate existing calculations but do not supply the new identity, continuity or evidence contracts.

## 18. Determinism Contract

The deterministic semantic result is fixed by:

```
canonical observations, including identities and metadata
+ complete estimator configuration and subject mappings
+ reference time
+ method/contract versions
```

The result must preserve identical:

```
field values
validity
confidence assessment
uncertainty assessment
freshness assessments
conflicts
limitations
evidence selection and ordering
snapshot summary
semantic content identity
```

No hidden clock, randomness, external fetch, mutable registry lookup or process-local continuity cache may affect it.

**Production metadata requires an explicit distinction.** The frozen `estimated_at` records when an artifact was produced. A replay performed later must not falsely claim that it ran at the historical reference time.

Therefore:

- The estimation core returns deterministic semantic content.
- Materialization attaches explicit `estimated_at` and production-artifact identity.
- Repeated production runs may have different production envelopes but the same semantic content identity.
- Exact whole-artifact equality additionally requires the same explicit production envelope.
- Loading an existing artifact restores its original envelope.

This is an explicit proposed equality contract requiring ADR acceptance, not a claim that different production timestamps are byte-identical.

Numerical ordering, precision and serialization conventions must belong to the method/schema version. UUID or row-ID sorting may break transport ties deterministically but must never create source event order.

## 19. Reconstruction / Persistence Decision

**Chosen architecture: both deterministic estimation and optional derived-state persistence.**

Three operations remain separate:

```
query evidence
    → restore canonical observations

estimate explicitly
    → compute a new versioned state artifact

load state
    → restore a previously stored artifact
```

`load_state` must never call the estimator.

Persistence contract:

- New derived artifacts belong to M3 Runtime Evidence Persistence.
- They do not enter M2 DecisionEvaluationRepository.
- Raw observations remain source authority.
- A persisted state is authoritative evidence of what the estimator produced, not replacement truth about the measurements.
- Save one complete snapshot atomically.
- Preserve fields, conflicts, limitations, configuration, methods, input references and production metadata.
- Same artifact identity with identical bytes is idempotent; different bytes under that identity are an integrity error.
- Corrections produce new artifacts with explicit supersession links.
- Missing retained input evidence makes independent re-estimation unavailable; it does not authorize recomputation or alteration during load.
- Unsupported artifact schema versions fail explicitly.
- Initial storage is additive; no implicit migration or rewrite of M2/M3.1 records.

Persistence is optional per request, but the implementation handoff should require the explicit save/load capability. An unsaved state must be labeled unsaved.

Concrete tables, indexes and storage layout remain implementation choices within this contract. This decision requires an ADR.

## 22. Economic Promotion Requirements

A value is promotable only when the required dimensions for that economic field are established:

1. Quantity semantics and source-contract version.
2. Provider identity and evidence attribution.
3. Relevant network/asset/pool/market identity.
4. Algorithm identity or algorithm/network binding when the quantity requires it.
5. Unit, denomination and conversion basis.
6. Observation/effective-time interpretation.
7. Acceptable age and quality.
8. Applicable account, payout or block scope.
9. Traceable source observation.
10. Explicit conflict assessment.

Promotion outcomes:

- `PROMOTED`
- `NOT_PROMOTED`
- `CONFLICTED`

A missing required dimension produces NOT_PROMOTED and an UNKNOWN canonical field. The original value remains raw context.

An unsupported identity or dimensional assertion produces an invalid candidate, not a guessed correction.

In particular:

```
miner pool difficulty ≠ network difficulty
configured payout coin ≠ mined asset
algorithm alias ≠ verified chain binding
accepted-share count ≠ proven credited economic work
```

- Difficulty: algorithm, difficulty convention and applicable block/regime.
- Block interval: protocol target versus measured historical interval.
- Reward components: subsidy/emission versus transaction fees, denomination and block applicability.
- Network hashrate estimate: estimation method/window and uncertainty; it must be labeled an estimate.

Reorganizations or competing chain anchors remain visible. The estimator does not silently select the highest height.

No provider is selected or implemented. Current absence produces UNKNOWN economic fields.

Future provider evidence requires a separately accepted versioned acquisition contract. It must not be mislabeled as `OBSERVER` or forced into M3.1’s frozen source enum.

- No implicit currency inversion or conversion.
- An explicit transformation must preserve both source evidence and method.

## 26. Economic Provider Conflict Contract

Preserve provider-specific observations before attempting canonical promotion.

Comparison requires matching:

```
quantity
network/asset/market or pool scope
units
effective interval
source semantics
```

Freshness and quality are evaluated for each candidate independently. They may establish ineligibility; they do not create an undocumented ranking among eligible providers.

Initial rule:

- One eligible candidate without unresolved comparable contradiction may be promoted.
- Multiple contradictory eligible candidates remain CONFLICTED; canonical value is null.
- Agreement does not prove independence when providers share an upstream source.
- No majority vote, average, “latest wins” or provider preference.
- Future selection requires an explicit versioned policy and retained conflict history.

This uses `StateConflict`; it does not create a second hidden conflict mechanism.

## 27. EconomicState vs Reward Boundary

EconomicState supplies contextual quantities and their evidence.

It does not calculate:

```
realized reward
expected future reward
net reward rate
reward target
target gap
action benefit
action utility
optimal action
```

Protocol block reward is a contextual source quantity. It is not the miner’s realized Reward.

Pool credited-work metadata is not an Outcome or attribution result.

M2 scoring, prediction confidence and Policy remain unchanged. Future RewardEvaluation must consume its own accepted Outcome and RewardContract semantics.

## 29. Performance / Bounded-Window Requirements

Every estimation request supplies finite:

```
lookback duration
record budget
decoded-byte budget
subject/field budget
continuity lookback
```

The accepted configuration must contain these limits; no unbounded defaults.

Requirements:

- No full-session scan as the normal estimation contract.
- No hidden expansion of the evidence window to obtain enough samples.
- No silent truncation, downsampling or dropping of conflicts.
- Deterministic pagination must finish within the total request budget.
- Input/provenance size remains bounded.
- Estimation failure cannot interrupt the miner.
- Persistence refusal does not claim the artifact was saved.
- Runtime duration instrumentation uses monotonic clocks outside semantic computation.

Exact operational budgets require explicit configuration in the later handoff/deployment profile. Their absence has defined failure behavior and does not authorize coding-time guesses.
