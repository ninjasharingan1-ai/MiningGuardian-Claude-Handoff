# Freeze blockers

## R4-01 — HIGH — RewardTargetController ownership contradicts RewardTargetAssessment ownership

The architecture ownership matrix correctly states:

```text
Target controller availability/state
    → Reward Target Controller

Target assessment quality/performance/gap/attainability
    → Reward Target Assessment subsystem
```

But an earlier architecture section still says the Reward Target Controller owns:

```text
current target state
gap-to-target
target attainability classification
```

These are now RewardTargetAssessment semantics.

### Risk

Codex could legitimately implement gap/attainability logic directly inside RewardTargetController despite the new assessment boundary.

### Required correction

Freeze ownership as:

```text
RewardTargetController owns:
    active-target consumption
    controller_status
    assessment orchestration
    reevaluation trigger orchestration

RewardTargetAssessment owns:
    assessment_quality
    current_reward_state
    performance_state
    signed_target_gap
    attainability
    attainability_reason
```

The controller may consume an assessment; it must not duplicate its semantic ownership.

---

## R4-02 — HIGH — ACTIVE and ASSESSMENT_UNAVAILABLE controller states overlap

Current invariants say:

```text
ACTIVE
    active_reward_target_id is required

ASSESSMENT_UNAVAILABLE
    active_reward_target_id is required
    target-seeking decision pressure = false
```

Nothing requires `latest_assessment_id` for ACTIVE or forbids it for ASSESSMENT_UNAVAILABLE.

Therefore the same persisted object can satisfy both semantic meanings.

### Required correction

Recommended frozen invariants:

```text
NO_ACTIVE_TARGET
    active_reward_target_id = null
    latest_assessment_id = null
    target-seeking pressure = false

ASSESSMENT_UNAVAILABLE
    active_reward_target_id required
    latest_assessment_id = null
    target-seeking pressure = false

ACTIVE
    active_reward_target_id required
    latest_assessment_id required
```

`ACTIVE` means an active target exists and an assessment artifact exists.

The assessment itself may still have:

```text
VALID
UNCERTAIN
STALE
INVALID
```

so controller availability remains separate from assessment quality.

---

## R4-03 — HIGH — RewardTargetAssessment optional fields lack the VALID-side invariant

The contract correctly says:

```text
assessment_quality != VALID
    signed_target_gap = null
    performance_state = null
    decision_evaluation_required = false
```

But it does not specify the inverse requirements for a VALID assessment.

Fields are declared optional:

```text
current_reward_state?
current_reward_uncertainty?
signed_target_gap?
performance_state?
```

A technically valid implementation could therefore produce:

```text
assessment_quality = VALID
signed_target_gap = null
performance_state = null
```

which contradicts the purpose of a valid target assessment.

### Required correction

Freeze these invariants:

```text
assessment_quality = VALID
    current_reward_state required
    signed_target_gap required
    performance_state required

assessment_quality != VALID
    signed_target_gap = null
    performance_state = null
    attainability = UNKNOWN
    decision_evaluation_required = false
```

`current_reward_uncertainty` may remain optional only if the selected reward-state method genuinely has no uncertainty representation; otherwise implementation-phase contracts may strengthen it.
