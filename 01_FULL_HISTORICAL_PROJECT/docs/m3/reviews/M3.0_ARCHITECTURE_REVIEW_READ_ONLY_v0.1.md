# M3.0 Architecture Review — Read-Only First Pass

**Review mode:** READ ONLY  
**Reviewed scope:** M3.0 canonical foundation documents against frozen M2 boundaries  
**Verdict:** FAIL TO FREEZE — remediation required before M3.0 acceptance / M3.1 implementation

## What is already structurally strong

- Frozen M2 ownership is preserved.
- ADR-0006 remains authoritative.
- Reward Target Control is first-class rather than optional.
- Prediction, Outcome, Reward, Decision, Action, and Execution are intentionally separated.
- Direct LLM actuation is prohibited.
- Safe Control includes capability, anti-churn, rollback, and restart-cost concerns.
- Time horizons are conceptually separated.
- Verification is cross-cutting and first-pass read-only.

## Findings

### F-01 — CRITICAL — Reward target setter and tracker are not separated

Current architecture gives the Reward Target Controller ownership over target identity, unit/basis, band, target state, gap, and attainability. The data contract contains only a generic `source/authority`.

Risk: a target-seeking controller that can also redefine its own target can move the goalposts and create false success.

Required correction:

```text
RewardTargetPolicy / TargetAuthority
    owns creation/change/retirement of target
        ↓
RewardTargetDefinition
        ↓
RewardTargetController
    owns tracking/gap/state only
```

Target changes must be versioned, auditable, and independent of current attainment.

### F-02 — CRITICAL — Reward semantics can double-count ADR-0006 penalties

The architecture describes the target as `risk-adjusted Expected Net Effective Reward Rate` while also listing ActionCost and uncertainty. Frozen ADR-0006 separately subtracts:

```text
Risk + ActionCost + Uncertainty
```

RewardEvaluation also currently allows:

```text
action_cost
risk/penalty components
```

Risk: the same risk/action cost/uncertainty may be penalized once in Reward and again in DUS.

Required correction:

- Define a first-class `RewardContract`.
- Make the Reward Target use a precisely defined economic reward metric.
- Keep decision risk/uncertainty penalties in ADR-0006 unless explicitly superseded.
- Realized economic transition costs may be part of realized reward if the RewardContract explicitly says so.
- Probabilistic risk/uncertainty must not be smuggled into realized reward.

### F-03 — HIGH — Outcome is too tightly coupled to Execution

Current Outcome contract requires:

```text
execution_id
action_id
decision_id
```

But M3.3 explicitly plans Reward Target / Outcome in observation/shadow form.

Risk: MiningGuardian cannot represent a valid reward/outcome window when no action occurred, which makes no-action baselines and target tracking structurally awkward or impossible.

Required correction:

Generalize Outcome to an observed evaluation result with optional attribution:

```text
Outcome
├─ PerformanceWindowOutcome
└─ ActionOutcome
```

or make execution/action references optional with an explicit `outcome_scope`.

### F-04 — HIGH — Reward/Pool evaluation window is not a first-class contract

The foundation correctly distinguishes:

- evaluation interval
- statistical horizon
- pool accounting window
- outcome window
- reward attribution window
- block interval

But there is no explicit object binding a Reward Target to the exact window being evaluated.

Required correction:

Add `RewardEvaluationWindow` / `RewardWindow` with:

```text
window_id
start/end
pool/chain context
accounting semantics
target_id
reward_contract_version
maturity status
data completeness
statistical horizon refs
```

This is especially important for the core requirement of reward performance inside pool time blocks.

### F-05 — HIGH — Economic / Blockchain Intelligence is scheduled too late

Current roadmap places:

```text
M3.7 Reward-target closed-loop optimization
M3.x Economic / Blockchain Intelligence
```

But reward targeting requires network difficulty, block interval, pool payout semantics, reward components, and economic conversion context before a meaningful target can exist.

Required correction:

Move Economic / Blockchain Intelligence into or before the state/economic context stage, before Reward Target shadow operation.

Recommended order:

```text
M3.1 Observability
M3.2 State + Economic/Blockchain Context
M3.3 Prediction
M3.4 Outcome/Reward + Target Shadow
...
```

Strategic LLM reasoning may remain later.

### F-06 — HIGH — Action authorization and Execution states are partially collapsed

`ExecutionRecord` currently suggests statuses including:

```text
REQUESTED
AUTHORIZED
BLOCKED
EXECUTING
SUCCEEDED
...
```

`REQUESTED`, `AUTHORIZED`, and `BLOCKED` belong before an execution attempt.

Required correction:

Separate:

```text
ActionRequest
ExecutionAuthorization
ExecutionAttempt / ExecutionRecord
RollbackRecord
```

Execution statuses should describe execution only.

### F-07 — HIGH — Post-decision `Policy/Safety Gate` creates policy ownership ambiguity

Frozen M2 says Policy owns candidate admissibility before Decision.

M3 Control Safety currently includes:

```text
DecisionResult
→ ActionRequest
→ Capability Gate
→ Policy/Safety Gate
```

Risk: this can become a second DecisionPolicy owned by Safe Control.

Required correction:

Rename/split the post-decision layer into execution-specific gates, e.g.:

```text
Capability Gate
Execution Safety Gate
Freshness Gate
Stability Gate
Authorization Gate
```

If state changes invalidate the selected candidate, return to Decision Engine for reevaluation rather than silently re-deciding inside Safe Control.

### F-08 — HIGH — Learning has no promotion boundary

`LearningArtifact` can describe model/calibration/action-cost updates, but there is no explicit rule separating learned evidence from activation in production.

Risk: later implementation could become self-modifying without independent validation.

Required correction:

```text
LearningArtifact
→ UpdateProposal
→ Offline/Replay Verification
→ PromotionDecision
→ Active Model/Knowledge Version
```

Learning must never mutate the active controller/model/policy directly.

### F-09 — MEDIUM — Raw post-action facts have dual ownership

Architecture currently states:

```text
Observed post-action facts | Outcome subsystem + Observability
```

Required correction:

- Runtime Observability owns raw observed facts.
- Outcome subsystem owns correlation, windowing, maturity, and outcome interpretation.
- Neither should share authoritative ownership of the same semantic artifact.

### F-10 — MEDIUM — Reward target lifecycle/state is incomplete

Current minimum states omit situations such as:

```text
NO_ACTIVE_TARGET
TARGET_EXPIRED / TARGET_STALE
TARGET_INVALID
```

Also `target_value or target_band` does not explicitly define the comparison mode.

Required correction:

Define target lifecycle and objective type, e.g.:

```text
MINIMUM
BAND
MAXIMIZE
```

with deterministic gap/state semantics.

### F-11 — MEDIUM — Outcome attribution needs a baseline/counterfactual contract

`attribution_quality` and `confounders` are present, but action learning requires an explicit comparison basis.

Required correction:

Add baseline/reference information:

```text
baseline_window
baseline_state
no-action/reference expectation
confounders
attribution method
attribution confidence
```

This prevents ordinary pool/network variation from being credited to an action.

### F-12 — MEDIUM — M3 persistence ownership is not yet explicit

The foundation correctly forbids overloading M2 persistence, but does not yet define who owns durable storage for:

```text
telemetry/event history
Outcome
Reward
PredictionError
LearningArtifact
RewardTarget history
```

Required correction at architecture level:

Define a separate M3 runtime/evidence persistence boundary. Implementation/storage technology can remain undecided.

## Freeze blockers

The following should be fixed before accepting M3.0:

```text
F-01 Target Authority
F-02 RewardContract / double-counting
F-03 Outcome without mandatory Execution
F-04 RewardEvaluationWindow
F-05 Economic Intelligence phase ordering
F-06 Authorization vs Execution states
F-07 M2 Policy vs Execution Safety gate
F-08 Learning promotion boundary
```

F-09 through F-12 should preferably be corrected in the same v0.2 architecture pass.
