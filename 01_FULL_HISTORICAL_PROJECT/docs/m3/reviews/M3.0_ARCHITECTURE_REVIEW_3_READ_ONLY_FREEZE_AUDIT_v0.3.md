# Freeze blockers

## R3-01 — HIGH — MINIMUM / BAND target-gap and state semantics are required but not defined

`M3_DATA_CONTRACTS_v0.3.md` now correctly limits RewardTarget to:

```text
MINIMUM
BAND
```

and says:

```text
target_gap and target_state must have deterministic semantics
```

but those semantics are not actually specified.

That leaves multiple valid-looking but incompatible implementations.

### Example ambiguity — MINIMUM

For:

```text
target_value = 100
current_reward_state = 110
```

possible implementations could produce:

```text
ABOVE_TARGET
target_gap = -10
```

or:

```text
WITHIN_TARGET_BAND
target_gap = 0
```

or another convention.

### Example ambiguity — BAND

For:

```text
band = [95, 105]
current = 101
```

does target_gap mean:

```text
0 because the value is acceptable
```

or:

```text
distance from center = 1
```

or:

```text
distance from nearest boundary
```

The architecture does not choose.

### Required correction

Define one canonical deterministic convention.

Recommended:

```text
MINIMUM

current < target_value
    state = BELOW_TARGET
    target_gap = target_value - current   # positive shortfall

current >= target_value
    state = ABOVE_TARGET
    target_gap = 0                        # no unmet gap
```

`WITHIN_TARGET_BAND` is not used for MINIMUM.

For BAND:

```text
current < lower
    state = BELOW_TARGET
    target_gap = lower - current          # positive shortfall

lower <= current <= upper
    state = WITHIN_TARGET_BAND
    target_gap = 0

current > upper
    state = ABOVE_TARGET
    target_gap = upper - current          # negative overshoot
```

If another sign convention is chosen, it must be explicit and consistent across glossary, contracts, evaluation, and tests.

`TARGET_UNCERTAIN`, `TARGET_INVALID`, `TARGET_STALE_OR_EXPIRED`, and `TARGET_UNREACHABLE_SAFELY` should define whether `target_gap` is unavailable/nullable or still meaningful.

## R3-02 — HIGH — NO_ACTIVE_TARGET is structurally impossible under current RewardTargetState fields

The canonical state vocabulary includes:

```text
NO_ACTIVE_TARGET
```

but the RewardTargetState contract currently requires:

```text
reward_target_id
reward_window_id
target_gap
```

without optional markers.

If there is no active target:

```text
reward_target_id = ?
target_gap = ?
```

has no legitimate value.

This forces implementation to invent sentinel values or fake identities, violating the architecture's own semantic discipline.

### Required correction

Make state-dependent optionality explicit.

Recommended contract shape:

```text
reward_target_state_id
reward_target_id?
reward_window_id?
evaluated_at
current_reward_state?
current_reward_uncertainty?
target_gap?
target_state
attainability?
attainability_reason?
freshness
evidence_refs
prediction_refs
decision_evaluation_required
```

Then define invariants:

```text
NO_ACTIVE_TARGET
    reward_target_id = null
    target_gap = null
    decision_evaluation_required = false

ACTIVE performance states
    reward_target_id required
    reward_window_id required when a reward window is being evaluated

TARGET_INVALID / TARGET_STALE_OR_EXPIRED
    reward_target_id required
    target_gap nullable unless valid comparison semantics still exist
```

Alternative: create a separate `RewardTargetControllerState` for NO_ACTIVE_TARGET and reserve `RewardTargetState` only for an actual target.

Either model is acceptable; one must be frozen.

# Medium findings

## R3-03 — MEDIUM — RewardTarget `status` is undefined and overlaps tracking-state terminology

The RewardTarget definition contains:

```text
status
```

while runtime tracking separately uses:

```text
target_state
```

No canonical meaning for `status` is supplied.

This risks mixing target-definition lifecycle with performance state.

### Required correction

Rename and define target-definition lifecycle explicitly, for example:

```text
lifecycle_status =
    DRAFT
    ACTIVE
    EXPIRED
    RETIRED
    SUPERSEDED
```

Keep this separate from:

```text
RewardTargetState.target_state
```

which describes runtime performance/tracking state.

---

## R3-04 — MEDIUM — Runtime action/execution evidence omits first-class authorization identity

`ExecutionAuthorization` is now a first-class contract and `ExecutionRecord` references:

```text
authorization_id
```

but `M3_RUNTIME_EVIDENCE_v0.3.md` action/execution evidence currently records:

```text
decision_id
candidate_id
action_id
execution_id
adapter_id
authorized/rejected gates
...
```

without `authorization_id`.

### Required correction

Add:

```text
authorization_id
authorization_status
authorization evaluated_at / expiry where relevant
rollback_id when rollback occurs
```

to runtime evidence/correlation requirements.
