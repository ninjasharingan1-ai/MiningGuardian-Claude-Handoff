## 4. Query Contract

`EvidenceQueryRequest` requires an aware UTC finite interval, explicit
source-observation or Guardian-receipt time basis, an as-of receipt cutoff,
explicit Guardian-session and source-instance association modes, source,
signal and exact top-level provenance selectors, and caller-supplied record,
byte, scan, filter, predecessor and pagination budgets. No operational limit
has a hidden default.

Session and source-instance modes distinguish all records, one exact identity,
and explicitly unassociated records. Duplicate filters and provenance keys,
ambiguous association scopes, unsafe selector keys, oversized selector values,
and incoherent predecessor budgets fail contract validation.

## 5. Retrieval Semantics

The implementation restores canonical `RuntimeObservation` payloads from the
existing M3.1 repository tables without changing their quality, freshness,
timestamps, identities or provenance. Source-time queries exclude records with
null `observation_time`; receipt time is never substituted. The as-of cutoff is
applied to `ingestion_time`, so evidence received after the cutoff is excluded.

Records are transported deterministically by selected time, ingestion time and
observation UUID. This ordering makes no source-event or physical simultaneity
claim. Adverse-quality records remain eligible for retrieval; S2 does not
perform temporal admission, continuity inference, conflict resolution or state
estimation.

## 6. Stable Pagination and Completeness

The query computes a SHA-256 dataset watermark over acquisition headers and
stored observation identities, ordinals and payload digests. Continuations bind
the request digest, watermark, offset and page. A changed dataset, changed
request or inconsistent continuation position fails with a typed exception.

Successful intermediate pages report `HAS_MORE`; only the terminal page reports
`COMPLETE`. Record, decoded-byte, scan-record, scan-byte and pagination budget
exhaustion returns a typed failure and never a truncated successful result.
Bounded predecessor evidence is returned separately on the first page and does
not authorize a cross-segment calculation.

## 7. Integrity and Read-Only Boundary

Before returning evidence, the reader verifies the existing table shape and
type affinities, acquisition schema version, header count, ordinal sequence,
payload SHA-256, canonical observation schema, row/domain identities and
acquisition-session coherence. Missing, malformed, orphaned or corrupted
evidence fails closed.

Tests captured executed SQL and found no insert, update, delete, create, drop or
alter statement. S2 adds no table, column, index or migration and does not

## 5. S2-C01 Root Cause

An unsigned cursor could preserve offset = page * page_size while skipping pages.
Request/watermark equality did not protect its position, and COMPLETE could follow
an omitted page.

## 6. Cursor Integrity Correction

Continuation v2 carries HMAC-SHA256 over every field except the MAC: cursor version,
ordering version, request digest, dataset watermark, next page and next offset.
The reader validates wire/schema content and verifies the MAC before database
access. Untampered cursors can be serialized and replayed with the same trusted
configuration. A different configuration key invalidates them. The key is supplied
only through trusted application construction, is excluded from configuration
serialization/repr, and never appears in cursor output. No key is generated or
hardcoded in production. Minimum key size is 32 bytes; the fixed wire bound is
2,048 characters for this fixed-size cursor schema. These are integrity-format
constraints, not hidden operational budgets. Applications must provision a secret,
unpredictable key and must not expose configuration construction to query callers.

## 7. Cursor Adversarial Tests

Direct tests reject offset-only, page-only, coherent offset/page, ordering-version,
request-digest, watermark, cursor-version and MAC changes before SQL. Malformed
JSON, empty/random structures, and oversized wire data are rejected. Tests also
cover valid continuation, final completeness, wrong filters/interval/time basis/
cutoff, different application key, changed dataset, and a signed but impossible
position constructed using the test's trusted key access.

## 8. S2-C02 Root Cause

Request maxima were caller-controlled, large SQL integers were not validated,
cycle scans were underreported, and payload/decoded byte checks ran after the
expensive materialization they purported to bound.

## 9. Trusted Resource Ceiling Design

`EvidenceQueryConfiguration` is an immutable required constructor argument to
`BoundedEvidenceQuery`. All deployment ceilings are mandatory and separate from
query requests: scan rows, scan bytes, canonical decode bytes, result rows,
filter terms, page size, page count, predecessor count and predecessor lookback.
There are no production operational defaults. Test limits and keys are explicit
fake application configuration. Every request limit must be within its configured
ceiling before database access. This adds no frozen configuration-file change.

## 10. Numeric Limit Validation

Counts/budgets require strict integers, reject booleans/fractions, and remain at
most 2**63 - 2, reserving one SQLite-safe sentinel. Positive/zero-permitted fields
retain their explicit constraints. Giant integers such as 10**100 fail request
validation and cannot reach SQLite. Query entry revalidates even validation-bypassed
model copies and reports typed S2 errors. Unrepresentable predecessor datetime
arithmetic also fails explicitly before SQL. Database read failures are wrapped
as typed S2 failures without logging input payloads or credentials.

## 11. Scan Record Accounting

Successful scanned_records = C + 2*O: C acquisition-header metadata rows,
O observation metadata rows, and O primary-key payload lookups. This counts
logical data-row visits, not SQLite B-tree page reads or schema-inspection work.
All successful work fits the one aggregate request/trusted scan budget. Refusal
can inspect one additional metadata-only sentinel; its payload is never fetched.
An exact two-cycle/two-observation fixture requires six row visits; budget five
fails. Fixed-width SQL identity/digest projections and integer-only projections
bound row metadata independently of payload bytes.

## 12. Scan Byte Enforcement

Before fetching full JSON, SQLite computes length(CAST(payload_json AS BLOB)).
The total stored UTF-8 payload bytes must fit maximum_scan_bytes. No payload-only
SELECT occurs until all candidate metadata passes both byte budgets. Header,
identity, digest and integer metadata bytes are excluded from this payload-byte
counter and bounded separately by fixed-width projection and aggregate row count.
An explicit SQLite BEGIN keeps metadata preflight and subsequent payload reads
inside the same read transaction, including with sqlite3 legacy transaction mode.
No table/index/migration or runtime write is introduced.

## 13. Decoded Byte Semantics

maximum_decoded_bytes means maximum stored canonical serialized UTF-8 bytes
admitted for canonical decoding during this query. It includes every decoded
candidate, even nonmatches and predecessors, because filtering dimensions remain
inside frozen JSON. It is enforced during metadata preflight, before payload
fetch and Pydantic decode. Result decoded_bytes reports this whole-query total,
not merely this page or matching records. It does NOT measure or promise a
portable Python heap limit. The same accounting is repeated for each page.

## 14. Oversized Observation Behavior

Oversized matching and nonmatching observations cause typed resource refusal
before full payload retrieval or canonical decode. Nothing is truncated, repaired,
skipped as complete, or partially returned. Four direct tests cover both byte
budgets and both filter outcomes using a 1,000,000-character payload.

## 15. Query Amplification Protection

Callers cannot raise trusted ceilings by changing request maxima. All nine
ceiling classes have direct refusal tests before SQL. Frozen storage still
requires bounded linear metadata scanning and post-decode filtering. Repeated
valid pages repeat bounded work; this API is not a request-rate limiter.
