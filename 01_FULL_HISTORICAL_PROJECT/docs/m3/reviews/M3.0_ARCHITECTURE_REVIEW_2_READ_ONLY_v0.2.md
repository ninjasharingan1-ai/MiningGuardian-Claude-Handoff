## R2-02 — HIGH — Top-level architecture diagram contradicts Reward Target ownership flow

The textual architecture correctly states:

```text
RewardTargetAuthority
→ RewardTarget
→ RewardTargetController
→ Decision evaluation
```

But the primary layer diagram visually places:

```text
Decision Engine
→ Reward Target Controller
→ Safe Control
```

This implies Reward Target Controller is downstream of Decision rather than a supervisory context that can trigger/feed Decision evaluation.

That topology could cause incorrect implementation.

### Required correction

Redraw the canonical architecture as:

```text
Economic / Runtime State
        │
        ├──────────────→ Prediction
        │
RewardTargetAuthority
        ↓
RewardTarget
        ↓
RewardTargetController
        ↓
RewardTargetState / Gap
        ↓
DecisionContext / Decision Evaluation
        ↓
M2 Decision Engine
        ↓
Safe Control
```

Target comparison after mature Reward then feeds the next control cycle.

## R2-03 — HIGH — `RewardTargetPolicy` reuses frozen M2 "Policy" terminology

Frozen M2 defines:

```text
Policy owns admissibility
```

v0.2 introduces the synonymous component name:

```text
RewardTargetAuthority / RewardTargetPolicy
```

Even though the intended responsibility is different, reusing `Policy` as another authoritative component creates semantic collision.

### Risk

Future implementation could confuse:

```text
M2 DecisionPolicy
```

with:

```text
RewardTargetPolicy
```

or incorrectly move target-governance rules into candidate admissibility.

### Required correction

Use one canonical component name:

```text
RewardTargetAuthority
```

If target governance rules are needed, they are rules/contracts owned by RewardTargetAuthority, not another generic `Policy` component.

Preserve:

```text
Policy = M2 candidate/action admissibility semantics
```

unless an explicit future ontology change is approved.

## R2-04 — HIGH — `MAXIMIZE` target type has undefined gap/state semantics

The RewardTarget contract allows:

```text
MINIMUM
BAND
MAXIMIZE
```

while RewardTargetState always contains:

```text
target_gap
target_state
```

`MAXIMIZE` has no finite target value or band by definition.

Therefore:

```text
gap to what?
WITHIN_TARGET_BAND relative to what?
ABOVE_TARGET relative to what?
```

is undefined.

### Required correction

Choose one of these models:

### Preferred

Keep RewardTarget as a setpoint/threshold contract:

```text
MINIMUM
BAND
```

and treat:

```text
MAXIMIZE
```

as a higher-level strategic optimization objective, not a RewardTarget objective type.

### Alternative

Define an explicit reference/baseline/frontier contract for `MAXIMIZE` with separate state semantics.

Do not leave one controller state machine serving incompatible target types.

## R2-06 — MEDIUM — Runtime Reward evidence still uses ambiguous `ActionCost`

The RewardContract correctly separates realized economic costs from ADR-0006 predicted ActionCost/Risk/Uncertainty.

But `M3_RUNTIME_EVIDENCE_v0.2.md` still records:

```text
ActionCost
transition cost components
```

inside realized Reward evidence.

### Risk

The old double-counting ambiguity can re-enter through evidence/storage naming.

### Required correction

Replace generic `ActionCost` in realized reward evidence with something explicit such as:

```text
realized_transition_cost
realized_restart_cost
realized_switching_cost
realized_operating_cost
```

as defined by the RewardContract.

Keep ADR-0006 `ActionCost` as a decision-time predicted penalty artifact.

---

## R2-07 — MEDIUM — M3 runtime persistence ownership remains incomplete

The data contract says Outcome/Reward/Learning require new repositories/streams and must not overload M2 persistence.

That preserves M2 correctly, but durable M3 ownership is still not explicit for:

```text
runtime telemetry/event history
RewardTarget / target-history
RewardEvaluationWindow
Action / Execution / Rollback
Outcome
Reward
PredictionError
LearningArtifact
PromotionDecision
```

### Required correction

M3.0 does not need to select SQL/database technology, but it should define a logical boundary such as:

```text
M3 Runtime Evidence Persistence
```

that owns durable runtime/evaluation facts while remaining separate from frozen:

```text
M2 DecisionEvaluationRepository
```

This is especially relevant before M3.1 Runtime Observability implementation.

---

## R2-08 — MEDIUM — Outcome attribution baseline is improved but still under-specified

v0.2 adds:

```text
baseline_window_ref?
attribution_method?
attribution_quality?
```

which is a meaningful improvement.

However action-attribution still lacks an explicit canonical representation for:

```text
baseline/reference state
no-action expectation
counterfactual/reference method
baseline compatibility
```

### Required correction

Do not attempt full causal-inference architecture in M3.0.

But require ACTION_ATTRIBUTED outcomes to declare a reference/baseline contract before their result can be used for Learning/Promotion.
