## 2. Purpose

M3.2 produces evidence-backed interpretations of **current** GPU, miner, and economic context from canonical M3.1 observations. It answers what the system defensibly knows at an explicit reference time. It does not predict a future value, evaluate reward, select an action, or execute anything. An honest `UNKNOWN` result is successful contract behavior when source semantics or evidence are insufficient.

## 10. Data Flow

```text
M3.1 stored RuntimeObservation (raw authority)
  → bounded, stable, integrity-checked query
  → subject/time/quality admission + explicit dispositions
  → field-specific continuity and conflict assessment
  → deterministic descriptive estimator + support/uncertainty assessment
  → requested-field StateSnapshot / EstimatedState semantic content
  → explicit production envelope
  → optional atomic derived-state save
```

`load_state` is a separate restore-only operation. An economic branch promotes only source values with complete field-specific semantics; otherwise it emits `UNKNOWN`/`NOT_PROMOTED` plus raw-context references. Provider acquisition, if ever authorized, occurs **before** estimation and outside the deterministic core.

## 11. Core Contracts

`EstimatedState` is a versioned evidence-backed interpretation for a subject at `T`, with state identity/type, structured fields, effective time `T`, truthful `estimated_at`, observation references, method/contract/configuration identity, freshness, field assessments, limitations and schema version. `EstimatedStateField` carries field/subject/estimand identity, typed value/unit, `T`, validity, confidence, dimensioned uncertainty, evidence completeness, freshness assessment, method/config, source references, conflicts and limitations; last-known context is separate. `StateEvidenceReference` retains observation UUID/schema/digest or immutable payload reference, nullable source instance, signal/unit, all recorded clocks, Guardian session/correlation, original and secondary quality, original freshness, M3.2 temporal assessment, disposition and reason. Non-null values require supporting observation IDs.

`FieldEvidenceContract` is versioned per estimand/subject and declares required/optional signals and source semantics, identity, units/conversions, quality admission, time basis/window, sample/span/coverage/gap minima, continuity, conflict rule, permitted degradation, confidence rubric, output domain and finite resource limits. Missing mandatory configuration is an explicit error. Mathematical minima do not prove sufficiency: at least one eligible value for mean/median/min/max, two ordered values for delta, two distinct eligible times and positive elapsed time for rate/slope, and an explicit denominator for missing fraction.

## 12. Evidence Query Boundary

The new read-only query companion must accept finite start/end and explicit source-time or receipt-time basis, as-of cutoff, Guardian-session selector (specific/unassociated/cross-session), source/source-instance/signal filters, subject/workload scope where available, maximum records, maximum decoded bytes, stable dataset snapshot/watermark, deterministic continuation, and bounded continuity-predecessor lookup. Return exact validated canonical records plus completeness and integrity status; include failure, stale, reset, and conflicting evidence relevant to selected signals. Null source time never falls back to receipt time. Deterministic transport order may use selected time, ingestion time and observation UUID, but it does not establish physical/source event order. Pagination must hold one stable evidence set; limit exhaustion cannot masquerade as complete. Incomplete required retrieval yields affected-field `UNKNOWN` or a typed failure. Do not prescribe indexes or migrations beyond the accepted semantics.

## 13. Temporal Admission Rules

The caller supplies aware-UTC `T`; all fields share it. Each field declares a finite `(T-W, T]` window. Source `observation_time` is source recording time; `ingestion_time` is Guardian receipt; optional event/processing times keep their distinct meanings. Evidence received after `T`, or known to have been canonicalized after `T`, cannot support an as-of current estimate. Unknown processing time does not prove historical consumption. Source recording clocks may be null: receipt-only evidence can describe what Guardian received, not source measurement age. Future/inconsistent clocks are excluded, never clamped fresh. Preserve M3.1 quality/freshness and record a separate M3.2 admission decision. Cross-source alignment needs proven subject, compatible quantity/unit/effective-time meaning and declared maximum difference; shared acquisition ID or receipt proximity is not simultaneity. Historical delayed/out-of-order evidence may be used only where the field method admits it with explicit ordering proof.

## 14. Continuity Rules

Segments are analytical evidence groups, not process incarnation. Retain source/source-instance, signal, subject/workload/algorithm, ordering basis, anchor, boundary evidence, proven incarnation if any, and method version. Break on explicit incarnation change, counter decrease/reset, recorded discontinuity, subject/workload/algorithm or counter-semantics change, excessive configured gap, unresolved ordering or identity conflict. Never calculate delta/rate across a boundary; require a new segment's own minimum evidence. Do not clamp negative deltas, assume rollover, derive share-production rate from receipt-only time, or infer miner restart from uptime/counter decrease. M3.1's in-process tracker is diagnostic only for reconstruction.

## 15. Conflict Rules

`StateConflict` records ID, affected field, kind, all participant evidence refs, comparison contract/version and basis, resolution status/reason, and any explicit resolution rule/version. Kinds include value disagreement, identity mismatch, temporal misalignment and unit/semantic mismatch. Compare only compatible subject/quantity/units/effective interval. Source failure and missingness are distinct from disagreement. Initially **no general cross-source winner**: no latest/preferred/highest/lowest source, average, vote or provider ranking. Unresolved comparable candidates make the current field `UNKNOWN`; a proven integrity/identity violation may make it `INVALID`. Any degraded conflict resolution requires a future accepted versioned field rule. Preserve all participants.

## 16. State Estimation Semantics

The first methods are explicit, versioned and deterministic: latest eligible observed value, arithmetic sample mean, median, min/max, within-segment delta, source-time counter rate, historical endpoint slope, and missing fraction with a defined expected-opportunity denominator. No implicit time weighting, smoothing, resampling or extrapolation. Historical slope describes the past and is not prediction. Reject non-finite outputs. Never combine algorithm-specific H/s as comparable economic output. A raw reading becomes an estimated current field only through an accepted field contract with defensible age, identity, quality and method assumptions. The initial GPU/miner set should be deliberately small; if current M3.1 source-clock evidence cannot satisfy a physical-current contract, emit `UNKNOWN` and separately labeled last-reported context instead of loosening the contract.

The initial S5 field-contract candidates are NVML `temperature_c`, `utilization_gpu`, `core_clock_mhz`/`memory_clock_mhz`, `power_w` and `throttle_reasons`; miner workload-scoped `hashrate_hs`, `accepted_shares`/`rejected_shares` and `uptime_seconds`; and miner API availability as **reachability only**. Each candidate needs a separate versioned estimand, subject/identity requirement, source-time/receipt interpretation, quality admission, unit, window and freshness configuration, and method. A physical-current value requires an established source recording-time basis; the current receipt-only NVML/miner evidence can instead populate separately labeled last-reported context. Share rates additionally require a proved within-segment source-time interval. A miner API success must never be promoted to mining health. Unknown GPU↔workload mapping stays unknown. This candidate list is an implementation scope limit, not an automatic permission to populate every field.

## 17. Confidence Semantics

`StateConfidence` means support for the particular estimated value under its method, not probability, M2 `DecisionConfidence`, observation quality, freshness or source authentication. Store `interpretation=CURRENT_ESTIMATE_SUPPORT`, rubric ID/version, `SUPPORTED`/`LIMITED`/`UNASSESSED`, identified checks with `PASS`/`FAIL`/`UNKNOWN`/`NOT_APPLICABLE`, reason codes, limitations and references. Minimum validity checks are distinct from strengthening checks. A `VALID` field can have `LIMITED` support. No numeric aggregate or HIGH/MEDIUM/LOW substitute.

## 18. Uncertainty Semantics

Represent measurement, temporal, source-disagreement, evidence-incompleteness, identity and method dimensions separately. Each has `QUANTIFIED`, `KNOWN_UNQUANTIFIED`, `UNKNOWN` or justified `NOT_APPLICABLE`, a reason and references. Quantification needs a justified magnitude/interval, unit, method/version, assumptions and coverage interpretation where applicable. `KNOWN_UNQUANTIFIED` retains null magnitude and a limitation; it does not claim quantified uncertainty. Unknown uncertainty is not zero, and uncertainty is not missing evidence.

## 19. Snapshot Semantics

Each requested field is explicit even when unavailable; unrequested fields are distinguishable. `VALID` and `DEGRADED` require non-null values; `UNKNOWN` and `INVALID` require null current-value slots, with positive violation evidence for `INVALID`. `DEGRADED` needs a named, versioned permitted rule. Summary is `COMPLETE` only if every requested field is `VALID`; `PARTIAL` if at least one field is `VALID` or `DEGRADED` but not complete; otherwise `UNAVAILABLE`. Structural contradictions, duplicate field identities or inconsistent reference times are construction/load errors rather than completeness states. Consumers declare their required subset and whether `DEGRADED` is usable. No universal `snapshot.is_safe` flag exists. A missing economic field does not erase a supported GPU or miner field.

## 20. Provenance / Versioning

For every field, retain requested and actual evidence windows; supporting, optional-support, conflicting, excluded and context-only observation references with reasons; input quality, secondary conditions and recorded freshness; M3.2 admission assessments; subject-resolution basis; conflict and continuity refs; exclusion counts; method name/version; field-contract and confidence-rubric versions; exact immutable configuration or retrievable equivalent plus digest; input-manifest identity; state schema version and limitations. Preserve exact raw algorithm, worker and rig strings. An algorithm registry resolution is a supplied immutable mapping snapshot, not a mutable lookup during replay. Shared miner raw-payload ancestry must prevent false independent corroboration of miner-derived pool metadata. Changes to selection, ordering, temporal admission, continuity, conflict, formulas or numerical behavior require an appropriate version change. Unknown method versions fail computation explicitly; compatible saved artifacts may still be restored without estimator execution.

## 21. Determinism

Fixed canonical observations including identity and metadata + complete immutable configuration/subject mappings + explicit `T` + fixed method/contract/schema versions must yield identical semantic values, assessments, conflicts, limitations, selection/order, summary and semantic content identity. No hidden wall clock, random UUID inside the semantic core, external provider fetch, mutable `latest` registry, process-local continuity history or unordered iteration may affect this result. Numeric precision, serialization and tie ordering belong to versioned method/schema behavior; UUID sorting may settle transport ties but cannot invent source event order. Materialization attaches explicit truthful production time `estimated_at` and production artifact ID. Replaying a historical `T` later may produce the same semantic content ID with a different envelope; exact full-artifact equality requires the same envelope. Never backdate `estimated_at` to `T` merely because the input is historical.

## 22. Derived Persistence

Provide both explicit reconstruction and optional per-request derived-state save/load. `query_evidence` restores canonical observations; `estimate` computes a new artifact; `load_state` restores an already persisted artifact and **MUST NOT invoke estimation** or fetch providers. Save a complete state snapshot atomically in a separate additive M3 derived-artifact owner: fields, validity, confidence, uncertainty, conflicts, limitations, requested scope, methods/contracts/configuration, all input references/dispositions, content identity, production metadata, schema and supersession. M3.1 raw observations remain source authority; the derived artifact records what an estimator produced. Do not alter M3.1 raw tables or use M2 `DecisionEvaluationRepository`. Identical bytes under an existing production artifact ID are idempotent; different bytes under that ID are an integrity error. Corrections create a new immutable artifact and explicit supersession. Unsupported schema/corrupt payload fails visibly. A failed or omitted save is explicitly unsaved. Loading preserves recorded assessments/envelope even if later raw evidence is unavailable; it never re-estimates. Concrete table/index layout is a later implementation choice; no implicit migration or rewrite of frozen history.

## 23. EconomicState Semantics

`EconomicState` is current economic/network/pool **context** at `T`, with identity/version, requested scope, independently assessed fields, completeness, source/provider refs, limitations and production metadata. Each `EconomicStateField` includes quantity, subject, unit/basis, effective-time meaning, quality/freshness assessment, provider refs, promotion result/reasons, and the same field validity/confidence/uncertainty/provenance obligations. `EconomicProviderReference` records provider identity, source/market/network scope, source-contract version, attribution/authentication status and evidence refs; an endpoint/label is attribution, not authentication.

Promotion outcomes are `PROMOTED`, `NOT_PROMOTED`, `CONFLICTED`. A field needs established quantity/source semantics, provider identity, relevant chain/asset/pool/market and algorithm binding when applicable, unit/denomination/conversion basis, source/effective and receipt times, quality/freshness, account/block scope, traceable evidence and explicit conflict assessment. Missing a required dimension means `NOT_PROMOTED` and an `UNKNOWN` canonical value; keep the raw value separately. A positive identity/dimensional violation is an invalid candidate, not guessed correction. Multiple contradictory eligible provider values remain `CONFLICTED` with null canonical value and retained participants; matching provider outputs do not prove independent origin.

Do not equate miner-reported pool `difficulty` with network difficulty; configured payout coin with mined asset; algorithm alias with verified chain binding; accepted shares with credited economic work; protocol block reward with realized miner reward; or `STATIC_CONFIGURATION` price assumptions with observed market price. Pool fee, payout scheme, minimum payout, conversion fee, payout asset and effective payout factor remain `UNKNOWN` until their account/policy/asset/effective-period meanings are established. Static assumptions may be separately represented with version/effective scope, never promoted as live observations. No revenue, expected reward, realized reward, reward target, gap or action utility is calculated here.

## 24. Provider Boundary

This handoff selects **no** live blockchain, market-price, exchange or pool-account provider and authorizes no network calls or credentials. A later separately accepted acquisition contract must establish chain/mainnet/testnet and asset identity, block anchor, difficulty convention, subsidy/fee components, block interval meaning, and source/effective/receipt times. Price evidence must establish base/quote asset, market/source, trade/bid/ask/index type, quote-per-base unit, times, quality, freshness and version. Pool economics needs pool/account tier, fee basis, payout policy and applicability. Until evidence exists, affected economic fields remain `UNKNOWN`.

An internal typed future-provider interface may be declared only if needed for these accepted contracts. It must not select a vendor, fetch data, assume authentication/freshness or force future source identity into M3.1's frozen `Source` enum (including misleading `OBSERVER`). If an additive source/acquisition contract is needed, stop and obtain separate acceptance before integration. Provider-specific evidence must remain separable for conflict analysis.

## 25. Security / Trust Requirements

**Handoff preparation: SECURITY_TEST_REQUIRED: NO. Later M3.2 implementation and independent verification: SECURITY_TEST_REQUIRED: YES.** Use safe local fakes/replay, not live attacks. Required adversarial cases: syntactically valid malicious observations; spoofed source/subject/provider identity; wrong coin, network or algorithm; unit/currency mismatch; future/manipulated timestamps; poisoned windows; duplicate flooding; conflict suppression; oversized windows/metadata and decoded-byte exhaustion; mutable registry/configuration; corrupt derived artifacts; secret-bearing metadata; provider disagreement and shared-upstream false independence. Prove that validation, a source label, checksum or matching reports do **not** establish truth or cryptographic authentication. Preserve M3.1 targeted redaction without broad sanitization of ordinary identity strings. No estimated or economic field may invoke control.

## 26. Resource / Performance Bounds

Every normal estimation request has finite configured lookback, maximum records, maximum decoded bytes, subject/field count, continuity-predecessor lookback and pagination budget. There is no unbounded full-session scan, hidden window expansion, silent downsampling or conflict dropping. Incomplete retrieval cannot be labeled complete; affected required fields become `UNKNOWN` or the operation returns a typed query failure. Exact deployment values are configuration inputs, not coding-time guessed defaults; missing mandatory values fail explicitly. Input and provenance serialization must stay bounded. Instrument query/estimation/persistence durations using monotonic time outside semantic computation. M3.1 fake-source overhead evidence is planning context, not real-machine M3.2 performance proof.

## 27. Failure Isolation

Query corruption, source unavailability, invalid identity, unknown method/configuration, resource refusal, estimator error and persistence failure produce typed, observable failures or field-level `UNKNOWN`/`INVALID` as the accepted contract permits. Failure in one independent field/domain does not erase other support. An unsaved artifact is never labeled saved; persistence refusal does not mutate raw evidence. Neither an estimation nor storage failure restarts/stops the miner, changes GPU settings, pool or algorithm, or triggers any actuator. Runtime failure logs must preserve source/operation identity while redacting known secrets and bounding amplification.

## 30. Testing Strategy

Use unit/contract tests for field invariants and deterministic methods; integration tests for read-only query and derived storage; property/invariant cases where they genuinely test combinations; replay for content identity and historical `T`; adversarial/security tests for trust boundaries; bounded-resource tests for record, byte and pagination failure. Critical cases:

- Validity/snapshot: missing ≠ zero, `UNKNOWN` ≠ `INVALID`, explicit `DEGRADED`, mixed and unavailable snapshots, requested versus unrequested fields.
- Confidence/uncertainty: quality/freshness cannot substitute for support; no probability; all three support and four dimension statuses; no made-up quantitative interval.
- Time/continuity: historical `T`, future/absent source clock, receipt-only and stale-only context, delayed/out-of-order evidence, reset/decrease/gap/algorithm change/unknown incarnation, and no cross-segment delta.
- Conflict/provenance: comparable disagreement, noncomparable units/subjects/times, identity violation, retained participants and exclusions, shared raw-payload ancestry.
- Persistence/determinism: exact save/load without estimator, unsupported schema/corruption, atomic rollback, idempotent identical artifact, same-ID/different-bytes failure, immutable supersession, shuffled input transport, stable semantic content versus changing production envelope.
- Economic: pool difficulty cannot populate network difficulty; payout preference cannot prove mined asset; absent binding/unit blocks promotion; static price stays configuration; provider conflicts remain visible.

No real miner/GPU changes or external provider calls are test prerequisites. Where evidence is unavailable, assert correct `UNKNOWN` rather than fabricate fixtures claiming real-world validation.
